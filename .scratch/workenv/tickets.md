# cubrid-workenv 구현 티켓

[승인된 명세](spec.md)를 9개 수직 구현 단위로 나눴다. 각 티켓은 자체 동작 검증을 포함한다. 모든 티켓은 ready-for-agent이며, 선행 티켓이 완료된 항목만 작업할 수 있다. 현재 시작 가능한 것은 01이다.

| 티켓 | 선행 | 사용자에게 제공하는 동작 |
| --- | --- | --- |
| [01: 첫 초기화부터 testdb 접속까지](issues/01-initialize-and-connect.md) | 없음 | 설치된 CUBRID를 선택한 worktree에서 init을 실행하고, 준비된 환경을 읽어 일반 cubrid·csql 명령으로 testdb에 접속하는 첫 동작을 완성한다. |
| [02: 재초기화·중단·동시 초기화의 안전한 처리](issues/02-initialization-state.md) | 01 | 이미 준비된 환경은 그대로 유지하고, 준비 도중 실패하거나 동시에 init이 들어와도 사용자가 현재 상태와 다음 조치를 알 수 있게 한다. |
| [03: 환경만 초기화하고 기존·외부 DB를 보존하며 사용](issues/03-database-selection.md) | 01 | init --no-db 이후 create-db로 DB를 준비하고, 기존 testdb나 외부 DB는 안전하게 재사용하며 관련 없는 registry 항목을 보존한다. |
| [04: 고갈된 자원 pool에서 삭제된 worktree 할당 회수](issues/04-allocation-reclamation.md) | 02 | pool이 꽉 찼을 때 삭제된 worktree의 실제 미사용 자원만 회수하고, 그렇지 않으면 소유 정보와 부족 이유를 보고한다. |
| [05: 서버·broker·PL의 worktree 간 공존](issues/05-multiple-instances.md) | 01 | 서로 다른 물리 DB를 가진 두 worktree에서 같은 DB 이름으로 서버·broker·PL을 사용하고 한쪽 stop이 다른 쪽에 영향을 주지 않게 한다. |
| [06: 상태를 바꾸지 않는 환경·DB·소유자 진단](issues/06-doctor.md) | 02, 03, 05 | doctor가 준비 상태, 선택된 설치, 자원 충돌과 DB 등록 문제를 읽어 설명하고 사용자가 수동 조치를 결정할 수 있게 한다. |
| [07: direnv와 빌드를 명시적 초기화 흐름으로 연결](issues/07-environment-integration.md) | 02 | 빌드·설치 후 사용자가 직접 init하고, 이후 디렉터리 진입은 준비된 환경만 빠르게 불러오는 실제 개발 흐름을 만든다. |
| [08: worktree 제거 시 내부 DB 정리와 외부 DB 보존](issues/08-database-lifetime.md) | 03 | 정상적인 작업 종료 후 worktree를 정리할 때 내부 DB는 함께 제거하고, 외부 또는 공유 DB와 사용자 파일은 보존하는 절차를 완성한다. |
| [09: 전체 개발 흐름 검증과 사용자·agent 안내](issues/09-complete-workflow.md) | 04, 06, 07, 08 | 완성된 기능을 실제 빌드·초기화·사용·진단·삭제 흐름으로 연결해 명세의 수용 기준을 확인하고 사용자가 따라 할 수 있는 안내를 제공한다. |

## 작업 순서와 완료

01 완료 후 02·03·05가 각각 시작 가능하다. 02 뒤에는 04·07, 03 뒤에는 08이 열린다. 06은 02·03·05의 상태·DB·resource 동작이 준비된 뒤 진행한다. 09는 나머지 모든 티켓이 직접 또는 간접 선행으로 완료된 뒤 통합 흐름을 확인한다. 병렬 실행은 가능한 의존관계를 설명할 뿐, agent 병렬 실행을 지시하거나 승인하는 것은 아니다.

구현자는 한 티켓의 선행 완료 여부와 현재 명세를 확인하고, 검증 결과를 해당 티켓에 남긴다. 상태 변경은 실제 구현·검증 결과에 따라 수행한다. 이 문서 작성으로 구현 티켓이 완료된 것은 아니다.

기존 구현 코드가 없는 저장소이므로 별도 prefactor 티켓은 만들지 않았다. 기존 도구 변경은 07의 사용자 흐름에 포함하고, 명세의 out-of-scope 항목은 티켓으로 되살리지 않는다.
