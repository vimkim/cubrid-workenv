# cubrid-workenv 요구사항

최종 구현 계약과 검증 기준은 [구현 명세](../.scratch/workenv/spec.md)를 따른다. 이 문서는 목표와 책임 범위를 요약한다.

이 문서는 요구사항 탐색 문답에서 합의한 호스트용 도구의 책임을 기록한다. CLI 이름은 `cub-workenv`이다. 프로젝트 홈은 `/home/vimkim/gh/cubrid-workenv`이다. 컨테이너 도구는 별도 프로젝트 `/home/vimkim/gh/cubrid-box`의 `docs/requirements.md`에서 구체화한다.

## 배경과 목표

출발점은 direnv가 느리다는 사용자 경험과 `cubrid-workenv`에 너무 많은 책임을 맡겼을 수 있다는 문제의식이다. 이 문서는 요구사항 합의이며, 실제 지연 시간이나 기존 구현의 원인을 분석한 보고서는 아니다.

에이전트는 서로의 작업을 추적하거나 실행 순서를 조율하지 않고 각자의 worktree에서 빌드·실행·테스트할 수 있어야 한다. 장시간 테스트 때문에 다른 에이전트가 실행을 기다리는 구조를 피한다. 에이전트가 시작하거나 종료한 서버와 테스트는 다른 작업에 영향을 주지 않아야 한다.

사람이 컨테이너 없이 호스트에서 테스트하는 흐름도 유지한다. 호스트에서 직접 테스트하는 동안 다른 에이전트가 컨테이너에서 테스트할 수 있어야 한다. 이때 요구하는 격리는 아래처럼 실행 방식에 따라 구분한다.

## 책임 구분

| 구성 요소 | 맡는 일 | 책임의 범위 |
| --- | --- | --- |
| `cubrid-workenv` | 호스트용 DB와 worktree별 설정 초기화 | DB 이름, 포트, UDS 경로, 설정 파일, shared memory 설정의 충돌 방지 |
| `cubrid-box` | 준비된 이미지를 지정된 mount 구성으로 실행 | 작업 간 간섭을 막는 컨테이너 실행 설정과 worktree별 데이터 경로 구성 |
| direnv | 호스트 작업에 필요한 환경변수와 PATH 설정 | 디렉터리 진입 시 DB 생성이나 빌드 등 초기화 작업을 수행하지 않음 |
| 사람과 에이전트 | 도구 호출 시점 결정, 빌드·실행·테스트·디버깅 수행 | 에이전트는 컨테이너 실행에 `cubrid-box`를 사용 |

여기서 자동화는 반복 가능한 작업을 CLI나 스크립트로 제공한다는 뜻이다. 도구를 언제 호출할지는 사람이나 에이전트가 결정한다. 디렉터리 진입만으로 모든 준비와 실행이 자동으로 일어나는 환경을 요구하지 않는다.

## 호스트에서의 직접 실행

`cubrid-workenv`은 사람이나 에이전트가 간단한 수정 사항을 확인할 때 사용할 DB들을 worktree별로 초기 생성한다. DB 이름은 서로 다른 worktree 사이에서 중복되어도 된다. 이름 자체가 아니라 master·broker·socket·shared memory 설정을 분리한다. 같은 물리 DB는 순차적으로 재사용할 수 있다.

초기화 범위는 DB 이름, broker 등 필요한 포트, UDS 경로, 설정 파일과 shared memory 설정을 포함한다. 해당 worktree의 연결 환경으로 의도한 DB를 사용하도록 하는 것이 목적이다. 기본 `init`은 `testdb`를 준비하며, `--no-db`는 DB 생성을 생략하고 이후 `create-db`를 사용한다.

초기화는 명시적인 명령으로 한 번 수행한다. worktree에 들어갈 때마다 같은 준비 작업을 반복하지 않는다. 여러 worktree의 CUBRID를 호스트에서 동시에 실행하는 사용 방식은 유지한다.

호스트 직접 실행은 설정 수준의 충돌 방지를 제공한다. 테스트 도구가 `pkill`로 다른 worktree의 서버를 종료하는 위험까지 차단하는 것은 요구하지 않으며, 사용자는 이 위험을 수용했다.

## 빌드와 도구 접근

사용자는 `just configure-build-and-install`로 configure → build → install을 명시적으로 수행한다. 설치가 끝나면 해당 실행 환경의 PATH에서 `csql`, `cubrid` 등 설치된 바이너리를 찾아 실행할 수 있어야 한다. 새 worktree 진입 시 자동 빌드를 요구하지 않는다.

테스트에 필요한 CTP, `cubrid-testkit` 등의 도구와 TC를 사용할 수 있어야 한다. 실제 실행 도구는 해당 테스트 흐름에서 선택하며, 이 요구사항이 모든 테스트를 하나의 도구로 통일한다는 뜻은 아니다.

에이전트는 명시적으로 컨테이너에 들어간 뒤 빌드·실행·테스트해도 된다. 컨테이너 작업에서는 바이너리와 테스트 도구 접근성이 컨테이너 안에서 충족되면 충분하다. 호스트의 `csql` 호출을 자동으로 컨테이너에 전달하는 기능은 요구하지 않는다.

## 완료 여부를 판단할 시나리오

아래는 후속 구현의 확인 기준이며, 이 문서 작성 과정에서 실행하거나 통과를 확인한 테스트는 아니다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| 명시적인 호스트용 초기화 | 기본 testdb 또는 환경만 준비하며, 다른 worktree와 자원 설정이 충돌하지 않음 |
| 호스트에서 여러 worktree의 CUBRID 실행 | 포트·UDS·설정 파일·shared memory 설정이 서로 충돌하지 않음 |
| DB에 접속 | 다른 worktree의 동명 DB에 실수로 접속하는 상황을 방지하도록 선택된 master와 registry 등 접속 환경이 구분됨; DB 이름 중복은 허용 |
| 초기화한 worktree에 다시 진입 | direnv가 환경변수와 PATH만 설정하며 DB 생성이나 빌드를 반복하지 않음 |
| `just configure-build-and-install` 완료 | 설치된 `csql`, `cubrid` 등을 해당 실행 환경의 PATH에서 찾을 수 있음 |
| 호스트에서 서버 이름을 대상으로 `pkill` 수행 | 다른 호스트 worktree의 서버에 영향을 줄 위험은 수용한 제한이며 격리 보장에 포함하지 않음 |

## 구체화된 동작

초기화 재호출은 경고 후 무변경이며 불완전 상태는 `doctor`로 안내한다. 진단은 읽기 전용이다. 숫자 자원은 정지한 worktree를 포함한 할당 기록으로 관리하고, pool 고갈 시 삭제된 worktree의 미사용 할당만 회수한다.

worktree 내부 DB는 worktree와 함께 삭제하고 외부 DB는 보존한다. HA는 향후 범위이며 CUBRID Manager는 제외한다. 모든 테스트에 `run`을 강제하거나 추가 DB 잠금을 기본 기능으로 넣지 않는다.

동일 물리 DB의 정상 경로 중복 실행 거부는 [실험](../experiments/native-db-exclusion/README.md)에서 확인했다. 이 결과는 전체 도구 구현이나 모든 비정상 경로의 검증을 의미하지 않는다. 구체적인 완료 기준과 구현자가 선택할 세부사항은 명세에 정리했다.

## 근거

이 문서는 사용자의 요구사항 탐색 대화에 근거한다. 운영 전제, 수용한 위험, 보존 범위와 도구 책임은 대화의 최종 답변을 반영했다. 후속 인터뷰와 native 실험에 따른 변경은 위 링크로 구분했다. 이 문서는 새 CLI나 컨테이너 런타임의 구현 완료를 주장하지 않는다.
